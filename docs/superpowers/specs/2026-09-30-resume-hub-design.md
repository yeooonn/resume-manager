# resume-hub 설계 문서

작성일: 2026-09-30
대상 사용자: 3년차 프론트엔드 개발자 (이직 준비 중)

---

## 1. 목적과 성공 기준

### 목적
채용 담당자가 다른 이력서와 구분해서 기억하는, 차별화된 마스터 이력서를 제작하고, 채용 공고별로 그 위에 맞춤 이력서를 파생시키고, 지원용 HTML/PDF 산출물까지 만들어내는 자동화 하네스를 만든다.

### 차별화 축 (설계 근간)
- 메인: **아키텍처/설계 사고** — "왜 이 구조를 택했고, 어떤 트레이드오프를 저울질했는가"를 프로젝트별 서사로 담아낸다.
- 병렬: **기술 깊이 + 오너십 서사** — 특정 기술 영역을 파고든 스토리와 "내가 왜 주도했는가"를 직접 서술한다.
- 목표 메시지: **"결정할 줄 알고 주도해서 끝내는 사람"**

### 성공 기준
1. 만들어진 기본 이력서를 읽었을 때, 프로젝트마다 "결정/대안/트레이드오프"와 "오너십" 서사가 최소 1회 이상 등장한다.
2. 이력서에 등장하는 모든 회사·수치·기술 스택이 `sources/profile.md`에서 정확히 검증 가능하다 (근거 없는 사실 0개).
3. 채용공고 URL 하나를 주면 5분 이내에 강도별 맞춤 이력서가 나오고, 강도 "강"에서도 사실은 절대 왜곡되지 않는다.
4. "다양한 프로젝트에 참여", "협업 역량", "책임감 있게" 같은 뻔한 표현이 이력서당 3개 이하로 억제된다.
5. 마크다운 이력서로부터 브라우저에서 그대로 인쇄해 PDF로 저장할 수 있는 HTML을 생성한다.

### 제약
- 기존 이력서 관련 스킬(`resume-builder`, `resume-feedback`)과 이전 스펙/플랜/실행기록은 새 하네스 완성 후 전량 제거한다.
- 기존 `sources/기존이력서.md`는 인터뷰 시작점으로도 사용하지 않는다 (뻔한 표현 오염 방지).
- 이 프로젝트에서 완결적으로 동작해야 하며, `config/repos.yaml`이 있는 이 저장소 컨텍스트에서만 실행된다.
- 외부 npm 의존성을 추가하지 않는다.

## 2. 전체 아키텍처

```
┌──────────────────────────────────────────────────────────┐
│ Layer 1 — 원자재 (한 번 만들면 두 스킬이 공유)              │
│   sources/                                                │
│     ├─ profile.md         ← 인터뷰 결과 + 판단/오너십 서사  │
│     └─ commits.json       ← git 로그 원본 (커밋별 요약)     │
└──────────────────────────────────────────────────────────┘
       ▲                                       │
       │ 생성/업데이트                          │ 읽기 전용
       │                                       ▼
┌────────────────────────┐        ┌────────────────────────────┐
│  /resume-base          │        │  /resume-tailor <URL>       │
│  ─────────────────     │        │  ─────────────────          │
│  ① profile 존재 확인   │        │  ① profile 로드             │
│  ② 없으면 인터뷰 진행  │        │  ② 공고 크롤(→ 텍스트 fallback) │
│  ③ 커밋 분석            │        │  ③ 강도 선택 (강/중/약)     │
│  ④ profile 저장         │        │  ④ 요건 ↔ profile 매핑     │
│  ⑤ 기본 이력서 생성    │        │  ⑤ 맞춤 이력서 생성          │
│  ⑥ 검토 라운드          │        │  ⑥ 사실 왜곡 검증 (필수)    │
└────────────────────────┘        └────────────────────────────┘
       │                                       │
       ▼                                       ▼
   resumes/이력서_기본.md              resumes/tailored/<회사>_yyyy-mm-dd.md
       │                                       │
       └───────────────┬───────────────────────┘
                       ▼
           ┌───────────────────────────────┐
           │  /resume-render <파일 경로>    │
           │  ─────────────────             │
           │  ① 마크다운 이력서 로드         │
           │  ② templates/resume-template.html에 삽입 │
           │  ③ HTML 저장                    │
           │  ④ 브라우저 인쇄 안내(→PDF)     │
           └───────────────────────────────┘
                       │
                       ▼
           output/<원본파일명>.html
```

### 핵심 원칙 3가지
1. **원자재 공유**: `profile.md`는 단일 진실 원천. 두 스킬이 이걸로부터 각기 다르게 하이라이팅한다.
2. **사실 불변**: 어느 스킬이든 `profile.md`에 없는 사실은 절대 만들지 않는다. `/resume-tailor`도 사실은 못 바꾸고 강조·서사만 조정한다.
3. **강도는 매번 선택**: `/resume-tailor` 실행 시점에 강/중/약을 결정한다.

### 형식 결정
| 항목 | 결정 | 이유 |
|---|---|---|
| 프로필 형식 | `markdown` | 사람이 직접 수정·확인하기 쉬움. 정형 헤딩으로 파싱 가능하게 강제. |
| 이력서 포맷 | `markdown` 우선 | HTML/PDF 변환은 별도 관심사, 이번 범위 밖. |
| URL 처리 | WebFetch 시도 → 실패 시 사용자 텍스트 붙여넣기 요청 | 한국 채용사이트는 SPA·봇 차단이 많아 fallback 필수. |
| 인터뷰 진행 | 카테고리 기반 라운드 | 아키텍처 판단·오너십·트레이드오프를 놓치지 않게 구조화. |

## 3. 인터뷰 카테고리와 프로필 스키마

### 3-1. 인터뷰 카테고리 (7블록)

| # | 블록 | 목적 | 핵심 질문 예시 |
|---|---|---|---|
| 1 | 기본 정보 | 필수 메타데이터 | 이름/연락처/GitHub, 총 경력, 관심·제외 도메인 |
| 2 | 커리어 서사 | 짧은 스토리 라인 | "왜 프론트인지", "지금까지의 궤적 요약" |
| 3 | **프로젝트 심층** ⭐ | 차별화의 핵심 | 각 프로젝트: What / Why / **아키텍처 결정+대안+트레이드오프** / **오너십(왜 내가 주도?)** / 문제 해결 / 결과·지표 / 회고 |
| 4 | **기술 깊이** ⭐ | 파고든 주제 | "특별히 파고든 기술 영역 하나만 꼽아라" — 성능/접근성/DX/상태관리/렌더링/빌드 등 |
| 5 | 협업·리더십 | 소프트 신호 | 리뷰·멘토링·크로스팀·의사결정 리드 사례 |
| 6 | 자기 인식 | 정직한 강약점 | 강점 3개(근거 필수), 개선 중인 약점 1-2개 |
| 7 | 지원 방향성 | 필터·톤 조정 | 원하는 회사·팀·제품 / 배제 조건 |

⭐ 표시된 블록 3·4가 차별화 축을 직접 담아내는 부분. 이 두 블록에서 대충 넘어가면 뻔한 이력서로 회귀한다.

### 3-2. 인터뷰 진행 규칙
- **분할 세션**: 한 번에 다 하지 않는다. `profile.md`는 언제나 재개 가능한 상태로 저장하고, 진행 위치를 `<!-- resume-at: 프로젝트 3, 오너십 -->` 형태 주석으로 남긴다.
- **기본 순서**: 블록 1·2 → 블록 3(프로젝트 심층)을 프로젝트별로 쪼개 세션마다 1~2개씩 → 프로젝트 전부 끝나면 블록 4·5·6·7 순서로 마무리
- **Follow-up 강제**: 각 질문 후 최소 1회 파고드는 재질문을 던진다. 예: "그건 다들 하는 얘기예요. 당시 구체적으로 어떤 순간이었나요?"
- **기존 이력서 금지**: `sources/기존이력서.md`는 열지 않는다. 표현 오염 방지.

### 3-3. 프로필 스키마 (`sources/profile.md`)

```markdown
---
name: 김연정
updated: 2026-09-30
positions_targeting: [프론트엔드 시니어, FE 엔지니어]
exclude_domains: [보안]
---

# 기본 정보
- GitHub / 블로그 / 이메일
- 경력: N년 M개월 (yyyy-mm ~ current)
- 최근 소속: <회사> · <팀> · <역할>

# 커리어 서사
왜 개발/프론트인지 (2-3문장), 지금까지 궤적 요약 (2-3문장)

# 프로젝트

## <프로젝트명> (yyyy-mm ~ yyyy-mm, <역할>)

### What (한 줄)
### Why (비즈니스 배경)
### 아키텍처 결정
- **결정**: 어떤 구조를 택했는가
- **대안**: 고려했던 다른 선택지
- **트레이드오프**: 무엇을 얻고 무엇을 포기했는가
- **결과**: 시간이 지나서 판단하면 옳았는가

### 오너십
- 주도한 범위 / 주도한 이유 / 배운 것

### 문제 해결 (1-3개 케이스)
- 문제 → 접근 → 해결 → 결과

### 임팩트 지표
- 정량(있으면) / 정성(반드시)

### 회고
- 다시 하면 바꿀 것

---

# 기술 깊이 — 파고든 주제
- 주제: <성능/접근성/DX/...>
- 계기 / 배운 것 / 사내외 공유 흔적

# 협업·리더십
- 리뷰·멘토링·크로스팀·의사결정 사례

# 자기 인식
- 강점 3 (근거 필수)
- 개선 중인 약점 1-2

# 지원 방향성
- 원하는 팀·제품 / 배제 조건
```

주석 표기 규약:
- `<!-- 커밋 근거 있음, 확인 필요 -->` : 커밋에는 있는데 인터뷰가 언급 안 한 성과
- `<!-- 근거 없음, 확인 필요 -->` : 인터뷰에 있는데 커밋 근거 없는 주장
- `<!-- resume-at: <위치> -->` : 인터뷰 중단 지점

## 4. 스킬 1 — `/resume-base`

### 4-1. Phase 1 — 데이터 수집 (병렬)

| 트랙 | 에이전트 | 인풋 | 아웃풋 |
|---|---|---|---|
| A | `interviewer` | 대화 (블록 1~7, 세션 재개 가능) | `sources/profile.md` (draft) |
| B | `commit-analyzer` | `config/repos.yaml`에 명시된 로컬 저장소들 | `sources/commits.json` |

- `interviewer` 규칙: 각 질문 후 follow-up 1회 강제. 프로젝트 심층 블록은 아키텍처 결정·오너십·트레이드오프를 반드시 파고든다.
- `commit-analyzer`: 각 저장소를 `git_author` 필터로 커밋 수집, 프로젝트별 그룹핑, 주요 기능·리팩토링·성능 개선 커밋을 자연어로 요약.

### 4-2. Phase 2 — 프로필 통합

`profile-integrator`가 `profile.md`와 `commits.json`을 대조:
- 커밋에는 있는데 인터뷰가 언급 안 한 성과 → `<!-- 커밋 근거 있음, 확인 필요 -->` 표시
- 인터뷰에 있는데 커밋 근거 없는 주장 → `<!-- 근거 없음, 확인 필요 -->` 표시
- 사용자가 이 표시들을 검토·확정한 뒤 다음 Phase로 진행

### 4-3. Phase 3 — 이력서 작성 (병렬 비평 3인)

```
                    ┌── cliche-detector ──┐
                    │  "다들 쓰는 표현" 찾아서 대체 제안       │
[resume-writer] ─초안─┤── differentiation-validator ─┤── 통합 재작성 ──> 이력서_기본.md
                    │  아키텍처/오너십 축 반영도 스코어링      │
                    └── fact-checker ─────┘
                       profile.md에 없는 사실 스캔
```

- `cliche-detector` 블랙리스트 표현 예: "다양한 프로젝트에 참여", "협업 역량을 갖춤", "책임감 있게", "완벽한 XX를 지향" 등 → 발견 시 profile 근거로 구체화를 요구.
- `differentiation-validator`: "결정/대안/트레이드오프" 언급 횟수, "주도/오너십" 언급 횟수를 세서 프로젝트당 최소 1회 미달이면 재작성 요구.
- `fact-checker`: profile에 없는 회사·프로젝트·수치·기술을 발견하면 **즉시 중단**.

`resume-writer`는 **최대 3라운드**까지 재작성. 3라운드 후에도 차별화 스코어가 미달인 경우: 3라운드 시점의 이력서는 정상 저장하되, 마지막에 "다음 프로젝트의 프로필 근거가 얇습니다: [프로젝트명 목록]. 인터뷰 추가를 권장합니다"라는 리포트를 사용자에게 별도로 출력한다.

### 4-4. Phase 4 — 사용자 검토
- `resumes/이력서_기본.md` 저장 후 스킬 종료.
- 사용자는 필요 시 `sources/profile.md`를 직접 수정하고 `/resume-base`를 재실행해 이력서를 다시 생성한다 (수동 루프).
- 이 스킬은 사용자 편집기와 상호작용하지 않는다.

## 5. 스킬 2 — `/resume-tailor <URL>`

### 5-1. Phase 1 — 공고 수집

```
① WebFetch(<URL>) 시도
   ├─ 성공: 본문 파싱 → job.md
   └─ 실패(SPA/봇 차단): "URL 크롤 실패, 공고 텍스트를 붙여넣어 주세요" → 사용자 입력
② job-parser가 공고 구조화 → resumes/jobs/<회사>_yyyy-mm-dd.md
   - 회사·팀·직무명
   - 필수 요건 (must)
   - 우대 사항 (nice-to-have)
   - 기술 스택 (mentioned)
   - 팀 문화·언급 (문화 신호)
   - 채용 배경 (있으면)
```

같은 URL 재실행 시 캐시된 `jobs/<회사>_<date>.md` 재활용 (덮어쓰기는 `--refresh` 명시 옵션).

### 5-2. Phase 2 — 강도 선택 + 요건 매핑

사용자에게 강도(강/중/약) 질문 후, `job-relevance-mapper`가 `profile.md`의 각 프로젝트/기술 항목을 공고 요건과 매핑해 `relevance-map.json`을 생성한다.

각 값은 해당 프로젝트가 공고 요건(must / nice / culture) 항목 중 몇 개를 충족하는지 카운트한다.

```
{
  "프로젝트1": { "must": 3, "nice": 2, "culture": 1 },
  "프로젝트2": { "must": 0, "nice": 1, "culture": 0 },
  ...
}
```

프로젝트의 관련도 총점 = `must * 3 + nice * 1 + culture * 1` (must에 가중치). 이 값으로 프로젝트 정렬·필터 기준을 삼는다.

### 5-3. Phase 3 — 강도별 재구성 로직

| 강도 | 섹션 순서 | 프로젝트 필터 | 헤드라인/요약 | 강조 표현 |
|---|---|---|---|---|
| **강** | 관련도 순 재정렬 | 관련도 낮은 프로젝트 축소·삭제 | **공고 맞춤 새로 작성** | 공고 키워드 반영 |
| **중** | 관련도 상위만 위로 | 유지 (분량만 조절) | 공고 톤 반영, 재작성 X | 부분 조정 |
| **약** | 유지 | 유지 | 유지 | 단어·어조만 변경 |

강도와 무관하게 **사실(what)은 절대 못 건드리고 해석·강조(how/why)만 조정**한다.

### 5-4. Phase 4 — 이력서 작성 + 강화된 병렬 비평

```
                    ┌── fact-checker (강화) ─┐
                    │  profile.md에 없는 것 감지 시 즉시 중단      │
[resume-writer] ─초안─┤── job-alignment-validator ─┤── 통합 재작성 ──> 이력서_<회사>_<date>.md
                    │  공고 must 요건이 이력서에 반영됐는지        │
                    └── cliche-detector ────┘
                       뻔한 지원 문구 방지 (기본과 동일)
```

- 강도 "강"에서도 새로 만드는 것은 오직 "표현·헤드라인·강조". 프로젝트·수치·기술은 절대 신규 생성 금지.
- 공고 must 요건 중 profile에 근거가 **전혀 없는** 것은 **이력서에 반영하지 않고**, 마지막에 별도 리포트로 사용자에게 "다음 must 요건은 반영 안 됨"을 알림.

### 5-5. Phase 5 — 산출물

```
resumes/
  ├─ 이력서_기본.md
  ├─ jobs/
  │   └─ <회사>_2026-09-30.md         ← 크롤한 공고 원문
  └─ tailored/
      └─ <회사>_2026-09-30.md         ← 맞춤 이력서
```

날짜를 포함하는 이유: 같은 회사에 여러 번 지원하거나 공고가 갱신되는 경우를 대비.

## 6. 스킬 3 — `/resume-render <파일 경로>`

이력서 마크다운 파일 하나를 인자로 받아 인쇄 친화적인 HTML로 렌더링한다. 콘텐츠 생성(스킬 1·2)과 렌더링을 완전히 분리해서, 이력서 콘텐츠가 바뀌지 않아도 템플릿만 개선하면 재렌더링할 수 있게 한다.

### 6-1. 인자와 기본 동작
- 필수 인자: 마크다운 이력서 경로 (예: `resumes/이력서_기본.md`, `resumes/tailored/토스_2026-09-30.md`)
- 선택 인자: `--out <경로>` — 기본값은 `output/<원본파일명>.html`
- 동작:
  1. 마크다운 파일 로드 및 검증 (파일 존재, 최소 헤딩 구조 확인).
  2. `templates/resume-template.html`의 `{{ CONTENT }}` 자리에 마크다운을 HTML로 변환해 삽입.
  3. `output/` 디렉토리에 HTML 저장.
  4. 사용자에게 "브라우저에서 열어 `Cmd+P` → 'PDF로 저장'" 안내 메시지 출력.

### 6-2. 템플릿 규격 (`templates/resume-template.html`)
- 단일 템플릿, 인쇄 지향.
- 화면 전용 배경/그림자 최소화, 인쇄 시 A4/Letter 모두 자연스럽게 나오도록 `@media print` 규칙 포함.
- CSS는 인라인 `<style>`로 포함해 외부 폰트/링크 의존을 없앤다 (system font stack 사용).
- 치환 토큰:
  - `{{ TITLE }}` — 이력서 제목(파일 첫 헤딩)
  - `{{ CONTENT }}` — 본문 HTML
  - `{{ GENERATED_AT }}` — 렌더링 시각 (yyyy-mm-dd HH:mm)
- 사용자가 CSS를 이후 자유롭게 수정할 수 있게 한 파일로 유지하고, 스킬은 이 파일이 없으면 경고 후 중단한다 (자동 재생성하지 않는다).

### 6-3. 마크다운 → HTML 변환 규칙
- CommonMark 기준 부분 지원(헤딩, 강조, 리스트, 인라인 코드, 링크, 표, 수평선). 이력서에 필요 없는 이미지·GFM 확장은 미지원해도 무방.
- 코드 블록은 `<pre><code>`로만 감싸고 syntax highlighting은 하지 않는다.
- `<!-- 커밋 근거 있음, 확인 필요 -->` 같은 주석은 HTML 결과물에서 제거한다 (검토용 표시가 노출되면 안 됨).

### 6-4. 산출물
```
output/
  ├─ 이력서_기본.html
  └─ 토스_2026-09-30.html
```

### 6-5. PDF 만드는 흐름 (사용자 관점)
1. `/resume-render resumes/이력서_기본.md` 실행 → `output/이력서_기본.html` 생성.
2. 안내에 따라 브라우저로 파일 열기 (`open output/이력서_기본.html`).
3. `Cmd+P` → 대상 "PDF로 저장" → 여백/스케일 조정 후 저장.
- 외부 도구(pandoc, Chrome headless 등)에 의존하지 않는다.

## 8. 안전장치와 검증

### 8-1. 안전장치

1. **사실 불변 원칙 (최상위)** — `profile.md`에 없는 회사·수치·기술은 어떤 이력서에도 절대 등장 못 함. `fact-checker`가 위반 즉시 프로세스 중단.
2. **인터뷰 중단 허용** — 사용자 "여기까지" 선언 시 profile에 `<!-- resume-at: ... -->` 표시 남기고 저장.
3. **재실행 안전 (idempotent)**
   - `/resume-base`: 기존 profile 있으면 "업데이트할 프로젝트 있나요?"로 시작
   - `/resume-tailor`: 같은 URL 재요청 시 캐시된 `jobs/<회사>_<date>.md` 활용 (`--refresh`로 덮어쓰기)
4. **git_author 미매칭 경고** — repos.yaml의 author와 매칭되는 커밋이 없는 저장소는 경고 후 스킵.
5. **미충족 공고 요건 리포트** — profile에 근거 없는 must 요건은 이력서에 반영하지 않고, 실행 마지막에 별도 리포트로 사용자에게 알린다.

### 8-2. 자동 검증 기준

이력서 품질은 사람 판단이지만, 다음은 자동 체크로 최소 기준을 강제한다.

| 체크 | 통과 조건 |
|---|---|
| profile 필수 섹션 | 기본 정보·서사·프로젝트(최소 1개)·자기 인식·지원 방향성 존재 |
| 이력서 사실 정합성 | 이력서 전체 회사·수치를 `profile.md`에서 `grep`으로 찾을 수 있어야 함 |
| 뻔함 표현 카운트 | 블랙리스트 표현 이력서당 3개 이하 |
| 차별화 축 반영 | 이력서에 등장하는 **각 프로젝트마다** "결정/대안/트레이드오프" 키워드 ≥1회, "주도/오너십" 키워드 ≥1회 |
| HTML 렌더 무결성 | `/resume-render` 실행 후 `output/*.html`이 생성되고, 파일에 마크다운 원문의 모든 헤딩(`#` 이상)이 대응 HTML 태그로 존재 |

### 8-3. 뻔함 감지 블랙리스트 (초기 목록, 확장 가능)

- "다양한 프로젝트에 참여"
- "협업 역량을 갖춤"
- "책임감 있게"
- "완벽한 ○○를 지향"
- "커뮤니케이션 능력"
- "빠르게 습득"
- "적극적으로"
- "성실하게"
- "열정적으로"
- "최선을 다해"

발견 시 `cliche-detector`가 `profile.md`의 구체적 근거로 대체 문장을 제안한다.
